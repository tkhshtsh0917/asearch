# 検索結果の順位

[English](../ranking.md)

不変索引の既定の順序は`(最小編集距離, order, key)`のままです。文書は最もよく一致するtextを使って1回だけ返します。ASIX v1のバイト列と一致判定は変わりません。

`QueryOptions::rank_by_position = true`（0.3以降）では、`(最小編集距離, 最も早い一致開始位置, order, key)`の順に並べます。開始位置は正規化後のUTF-16の0始まりのオフセットです。同じ距離ならオフセット1からの一致は2からの一致より上位になり、完全一致は開始位置が早い曖昧一致より引き続き上位になります。別名の間では最小距離、最も早い開始位置、入力text順の順に選びます。記号を一つも消費しない対応付けの開始位置は`usize::MAX`で、同距離の中では最後になります。

まず検索器が一致するtextと最小距離を求めます。次に再利用する動的計画法の1行で、上位件数外の別名も含む、生存するすべての一致textについて、その最小距離における最も早い開始位置を求めます。リテラル・置換・有料の挿入遷移は一致範囲を消費しますが、Include／ワイルドカードの無料ループは消費しません。候補全体を並べ替えてから件数を制限します。生存するセグメントの結果も同じ順序で統合するため、差分と圧縮後の表示で結果が揃います。開始位置による順位は説明用の決定的なハイライト規則とは別で、ハイライト範囲を変えません。

作業領域の生成時に行バッファを予約し、既存の作業メモリ予算へ計上します。無制限の経路復元行列は確保しません。位置順位には、一致textの長さとクエリのリテラル長の積、および候補の整列に比例する処理が加わります。既存の順序と性能を維持するため明示的に有効化します。インクリメンタル／絞り込みキャッシュは一致候補の選択を引き続き担当し、各クエリで完全な一致集合から順位を計算し直します。

WASMの検索設定ABIは従来の7ワード（既定順序）、または末尾に真偽値のフラグを加えた8ワードを受け付けます。`0`は既定順序を維持し、`1`は位置順序を選びます。それ以外の長さやフラグ値は拒否します。位置順序のpacked結果は、通常のhitとtotalsの後にhitごとの開始位置を追加し、記号を消費しない場合は`0xffffffff`とします。既定順序のpacked結果は従来のレイアウトを維持します。デモのTypeScriptアダプターは`ranking: "position"`と省略可能な`SearchResult.starts`を公開します。結果のコピーは開始位置も保持し、シャードの統合には同じ順位モードが必要です。Intent DAGの検索は従来の独自の順序を維持し、このオプションを受け付けません。

検索ごとに、64×1,024×1,024回の位置遷移という固定上限をsegment列全体で共有します。各segmentは、自身の位置DPの前に、生存する全一致別名の`正規化UTF-16 text長×コンパイル済みリテラル数`という上界を計上します。超過時は部分的な順位を返さずRESOURCE_LIMITです。limit=0の総数は位置処理を省き、リテラルが空のpatternはDP遷移を消費しません。このCPU処理上限は設定可能なメモリ予算とは別です。

sessionのcache計画は最初のquery設定が分かる前に最大の位置結果転送領域を予約し、checkpointが結果用の余裕を使い切らないようにします。

位置計算の処理量で拒否された場合は、該当segmentのplannerとcheckpointを無効にします。拒否された接頭辞を延長する場合も、次のqueryはsessionのresetを要求せず完全な候補を再計算します。不完全な候補履歴は再利用しません。

既定順序のRust検索はSearchHit.startを計算せずusize::MAXのままとし、TypeScriptアダプターは既定modeでstarts自体を省略します。
